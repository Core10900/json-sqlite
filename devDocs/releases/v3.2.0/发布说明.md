# v3.2.0 npm 发布说明

> 包名：`@webofcat/jsonsqlite`  
> 功能与测试：[开发计划.md](./开发计划.md) · [功能测试计划.md](./功能测试计划.md)  
> **非 LTS。** 本版也不是设计完工版。本文件管注册表标签、安装包里的文字，以及 git tag 和 GitHub Release。功能做完但标签没核对，这一版不算发出去。提交在 `main` 上、npm 也能装到本版，但远程没有 `v3.2.0` 和 GitHub Release，同样不算发出去。

不带版本号的 `npm view @webofcat/jsonsqlite` 读的是 `latest`，不是仓库里的最高版本号。2.5.0 只用 `lts-3` 发布时，这条命令一直显示 2.4.0。

`lts` 是生产 pin。`latest` 是当前发布的最新版本。这一版不动 `lts`，但必须把 `latest` 移到 3.2.0。

## 1. 发布后的标签

发布前先执行 `npm view @webofcat/jsonsqlite dist-tags --json`，记下当时的值。

| 标签 | 发布后 |
|------|--------|
| `latest` | **3.2.0** |
| `lts` | 与发布前相同，应为 **2.2.0** |
| `lts-2` | 与发布前相同，应为 **2.2.0** |
| `lts-3` | 与发布前相同，应为 **2.5.0** |

不新增 `lts-4`。不删除已有标签。

## 2. 先改安装包里的文字，再 publish

这些文件打进 tarball 或被 `npm view` 直接显示。publish 之后再改，已经发出的 3.2.0 不会变。

| 位置 | 要求 |
|------|------|
| `packages/core/package.json` 的 `version` | `3.2.0` |
| 同文件的 `description` | 含 `3.2.0`、`not LTS`、不是设计完工、生产 pin 仍是 2.2 |
| `packages/core/README.md` | 文首版本是 3.2.0、非 LTS，并写明设计完工线是 3.6。不带 tag 的安装得到 `latest`（3.2.0）。`lts` / `lts-2` 是 2.2，`lts-3` 是 2.5。Redis、autoFix 默认关闭 |
| `packages/core/config.example.json` | 含本版新增且默认关闭的字段：`l3` / `redis`、`timeTravelRetentionMs`、`transactionTimeoutMs`、`alerts.responseTimeMs`、`autoTuneMinHits`、`metricsIntervalMs`。未实现的 `replica`、`cluster`、`graphql`、`wasm` 不出现 |
| 同目录 `package.json` 的 `exports` | 含 `"./plugin"`。深路径 `dist/` 不是公共入口 |
| 仓库根 `README.md`、`CHANGELOG.md` | 与上面同一套标签句子。性能数字只引用 `devDocs/releases/v3.2.0/性能包络.md`，不把另一套数字写进安装包 README |

`description` 使用这一句：

```text
JSON-native embedded database for Node.js — 3.2.0 single-node ops (not LTS; not design-complete; production pin remains 2.2)
```

性能包络留在仓库。不要把 bench 原始数据打进 tarball。不要出现 LTS-4、设计完工、Vision Complete。

## 3. 发布命令

在 `packages/core` 执行。仓库根是 `"private": true`，不能在根目录 publish。

```bash
pnpm publish --access public
```

不要加 `--tag`。默认就会把 `latest` 指到 3.2.0。`prepublishOnly` 会先 build 再跑测试；测试失败就不要绕过它发版。

```bash
# 不要这样发 3.2.0
pnpm publish --access public --tag lts-3
```

## 4. 发出后立刻核对

```bash
npm view @webofcat/jsonsqlite version
npm view @webofcat/jsonsqlite description
npm view @webofcat/jsonsqlite dist-tags --json
```

通过标准：

- `version` 是 `3.2.0`。若仍是 3.1.x，就是 `latest` 没动。
- `description` 含 `3.2.0` 和 `not design-complete`。
- `latest` 是 `3.2.0`。`lts`、`lts-2`、`lts-3` 的版本号与发布前相同。

没通过时只改标签，不要为了改标签再 publish 一次：

```bash
npm dist-tag add @webofcat/jsonsqlite@3.2.0 latest
npm view @webofcat/jsonsqlite version
```

三条命令都符合上一节之前，不要在 GitHub Release 里写「已发布」。通过后按第 5 节打 tag 并创建 Release。

---

## 5. Git tag 与 GitHub Release

npm publish 不会创建 git tag，把版本提交推进 `main` 也不会。GitHub 的 Releases 页只列出由 tag 创建的 Release。2.5.0 的提交已经在 `main` 上，npm 也能装到 `2.5.0`，远程却没有 `v2.5.0`，Releases 页就只显示到 `v2.2.0`。

第 4 节核对通过之后，在仓库根打 tag。tag 打在把 `packages/core/package.json` 的 `version` 改成 `3.2.0` 的那次提交上。之后只改文档、版本号仍是 `3.2.0` 的提交，不作为这个 tag 的目标。

```bash
git tag v3.2.0 <发布提交>
git push origin v3.2.0
```

tag 推上去之后，用 `v3.2.0` 创建 GitHub Release。只推 tag 时，tag 出现在 Tags 页，Releases 页没有这条。标题为 `v3.2.0`，标明非 LTS，不写设计完工。正文与 `CHANGELOG.md` 里 3.2.0 一节一致。

核对：

```bash
git ls-remote --tags origin refs/tags/v3.2.0
```

这条命令有输出，并且 https://github.com/Core10900/json-sqlite/releases/tag/v3.2.0 能打开，开发计划里的「发布」才可以勾。没有 tag，或只有 tag、没有 Release，都不算发出去。

`3.2.x` 补丁用同一规则。tag 名是 `v` 加该补丁的版本号，打在该补丁自己的版本提交上，并单独建一条 Release。

## 6. 3.2.x 补丁

补丁只修正确性和安全，不新增命令，不改默认值。

- 当时没有更高的 3.x 占据 `latest`：补丁版本发布后，`latest` 改为该补丁。
- 3.3 或更高版本已经是 `latest`：只发布 `3.2.x`，不移动 `latest`，也不移动任何 `lts*`。
- 补丁的 `description` 仍写明非 LTS、不是设计完工。
- 补丁同样要有远程 tag `v3.2.x` 和对应的 GitHub Release，见第 5 节。
