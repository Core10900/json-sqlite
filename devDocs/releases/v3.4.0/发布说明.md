# v3.4.0 npm 发布说明

> 包名：核心仍是 `@webofcat/jsonsqlite`  
> 功能与测试：[开发计划.md](./开发计划.md) · [功能测试计划.md](./功能测试计划.md)  
> **非 LTS。** 子包可以另发，但不能抢走核心包的 `latest`。核心包的提交在 `main` 上、npm 的 `latest` 也已是本版，但远程没有 `v3.4.0` 和 GitHub Release，同样不算发出去。

不带版本号的 `npm view @webofcat/jsonsqlite` 读的是核心包的 `latest`，不是仓库里的最高版本号。2.5.0 只用 `lts-3` 发布时，这条命令一直显示 2.4.0。

`lts` 是生产 pin。`latest` 是核心包当前发布的最新版本。这一版不动 `lts`，但必须把核心包的 `latest` 移到 3.4.0。

## 1. 发布后的标签

发布前先执行 `npm view @webofcat/jsonsqlite dist-tags --json`，记下当时的值。

| 标签 | 发布后 |
|------|--------|
| `latest` | **3.4.0** |
| `lts` | 与发布前相同，应为 **2.2.0** |
| `lts-2` | 与发布前相同，应为 **2.2.0** |
| `lts-3` | 与发布前相同，应为 **2.5.0** |

不新增 `lts-4`。不删除已有标签。

---

## 2. 先改安装包里的文字，再 publish

这些文件打进核心包 tarball 或被 `npm view` 直接显示。publish 之后再改，已经发出的 3.4.0 不会变。

| 位置 | 要求 |
|------|------|
| `packages/core/package.json` 的 `version` | `3.4.0` |
| 同文件的 `description` | 含 `3.4.0`、`not LTS`、复制默认关闭、生产 pin 仍是 2.2 |
| `packages/core/README.md` | 文首版本是 3.4.0、非 LTS，并写明仍然没有自动选主。不带 tag 的安装得到核心包 `latest`（3.4.0）。`lts` / `lts-2` 是 2.2，`lts-3` 是 2.5 |
| `packages/core/config.example.json` | `graphql` 出现且默认关闭。`cluster`、`wasm` 仍不出现 |
| 仓库根 `README.md`、`CHANGELOG.md` | 与上面同一套标签句子 |
| 《JSONSQLite npm包与后端接入说明》 | 若本版要拆包，先改这份说明里的包名和安装命令，再 publish 子包 |

`description` 使用这一句：

```text
JSON-native embedded database for Node.js — 3.4.0 replication and access layer (not LTS; replication default off; production pin remains 2.2)
```

不要出现 LTS-4、设计完工、Vision Complete、自动选主。不要把向量插件写成通用向量库。核心包的 `package.json` 不把 Express、Nest 或 LLM SDK 写成 dependency 或 peerDependency。

### 子包

GraphQL、Express/Nest 示例、向量插件可以是独立包。规则：

- 接入说明还没写上包名和安装命令时，不 publish 子包。
- 子包用自己的名字和版本号。不要把子包发布成 `@webofcat/jsonsqlite` 的某个 tag。
- 子包的 `latest` 只属于那个包。核对核心包时仍然看 `@webofcat/jsonsqlite`。
- 子包 description 写明可选、失败不影响核心包查询。向量包写明不是通用向量库。

## 3. 发布命令

先发核心包。在 `packages/core` 执行。仓库根是 `"private": true`，不能在根目录 publish。

```bash
pnpm publish --access public
```

不要加 `--tag`。`prepublishOnly` 会先 build 再跑测试；测试失败就不要绕过它发版。核心包核对通过之后，才按接入说明发布子包。子包同样不要使用会让人以为它是核心包 `latest` 的名字。

```bash
# 不要这样发核心包
pnpm publish --access public --tag lts-3
```

## 4. 发出后立刻核对

```bash
npm view @webofcat/jsonsqlite version
npm view @webofcat/jsonsqlite description
npm view @webofcat/jsonsqlite dist-tags --json
```

通过标准：

- `version` 是 `3.4.0`。若仍是 3.3.x，就是核心包的 `latest` 没动。
- `description` 含 `3.4.0`。
- `latest` 是 `3.4.0`。`lts`、`lts-2`、`lts-3` 的版本号与发布前相同。

每个实际发出的子包再执行一次 `npm view <子包名> version`。版本号必须是接入说明里写的那个。

核心包标签不对时只改标签，不要为了改标签再 publish 一次：

```bash
npm dist-tag add @webofcat/jsonsqlite@3.4.0 latest
npm view @webofcat/jsonsqlite version
```

核心包三条命令都符合上一节之前，不要在 GitHub Release 里写「已发布」。通过后按第 5 节打 tag 并创建 Release。

## 5. Git tag 与 GitHub Release

npm publish 不会创建 git tag，把版本提交推进 `main` 也不会。GitHub 的 Releases 页只列出由 tag 创建的 Release。2.5.0 的提交已经在 `main` 上，npm 也能装到 `2.5.0`，远程却没有 `v2.5.0`，Releases 页就只显示到 `v2.2.0`。

第 4 节核对通过之后，在仓库根打 tag。tag 打在把 `packages/core/package.json` 的 `version` 改成 `3.4.0` 的那次提交上。之后只改文档、版本号仍是 `3.4.0` 的提交，不作为这个 tag 的目标。子包不另打本仓库的 tag。

```bash
git tag v3.4.0 <发布提交>
git push origin v3.4.0
```

tag 推上去之后，用 `v3.4.0` 创建 GitHub Release。只推 tag 时，tag 出现在 Tags 页，Releases 页没有这条。标题为 `v3.4.0`，并标明非 LTS。正文与 `CHANGELOG.md` 里 3.4.0 一节一致。

核对：

```bash
git ls-remote --tags origin refs/tags/v3.4.0
```

这条命令有输出，并且 https://github.com/Core10900/json-sqlite/releases/tag/v3.4.0 能打开，开发计划里的「发布」才可以勾。没有 tag，或只有 tag、没有 Release，都不算发出去。

`3.4.x` 补丁用同一规则。tag 名是 `v` 加该补丁的版本号，打在该补丁自己的版本提交上，并单独建一条 Release。

---

## 6. 3.4.x 补丁

补丁只修正确性和安全，不新增命令，不改默认值，不加选主。

- 当时没有更高的 3.x 占据 `latest`：核心包补丁发布后，`latest` 改为该补丁。
- 3.5 或更高版本已经是 `latest`：只发布 `3.4.x`，不移动 `latest`，也不移动任何 `lts*`。
- 子包补丁只移动该子包自己的 `latest`。子包补丁不另打本仓库的 tag。
- 核心包补丁同样要有远程 tag `v3.4.x` 和对应的 GitHub Release，见第 5 节。
