> 主题：**多写者长期稳定线（LTS-3）**  
> 前置：**2.4.0** 的冲突、死锁、崩溃注入已绿，并经过浸泡期（建议至少一个 minor 周期，期间只修 2.4 缺陷）

## 1. 为什么 2.5 可以当 LTS，以及它和 2.2 的分工

2.4 是多写者第一次实现，不能在实现的同一版上宣布长期稳定。2.5 只冻结 2.4 已经跑绿的契约。

| 线 | 谁应该 pin |
|----|------------|
| **LTS-2 = 2.2.x** | 单写者生产。不需要多进程写就留在这里 |
| **LTS-3 = 2.5.x** | 需要同一台机器多进程写。默认仍是单写者，因此从 2.2 升上来不会自动变成多写者 |

LTS-3 承诺：

- 默认 single 的行为不低于 LTS-2 的正确性红线。  
- `writers: 'multi'`、SERIALIZABLE、死锁错误码、savepoint 的文档语义在 `2.5.x` PATCH 中不缩小。  
- 不在 PATCH 里加入复制或集群。  
- 与 LTS-2 并行维护。安全补丁两条线都要评估。

本版交付物是回归、迁移说明（2.2 → 2.5，默认不改写者模式）、兼容信息 `lts: true` 且线名为 `2.5`、冻结包含 `--writers` 的 CLI 面。

### 不做

新存储格式、复制、GraphQL、选主。

## 2. 文档交付：同步更新 `packages/core/README.md`

本版开发完成、勾选验收之前，必须在同一次交付里更新 [`packages/core/README.md`](../../../packages/core/README.md)。2.5 不增加功能，README 要写的是两条 LTS 怎么选、默认会不会变、哪些语义被冻结。只改版本号不算完成。

写作要求：

- 与 2.4 已经跑绿并在本版冻结的契约一致。不在 README 里扩写 2.4 没有的行为。
- 读者要能只看这个文件决定留在 2.2 还是升到 2.5，并知道升级后默认仍是单写者。
- `getCompatibilityInfo()` 与 `version --json` 的示例可复制，字段与实现一致。
- 文首写明 **2.5.0、LTS-3**。主推荐若仍是单写者，文首就写继续 pin **LTS-2（2.2）**。

本版 README 必须写清：

1. 两条线的分工，用对照而不是一段形容词：
   - **LTS-2 = 2.2.x**：单写者生产。不需要多进程写就留在这里。
   - **LTS-3 = 2.5.x**：同一台机器上的多进程写。默认仍是单写者，从 2.2 升上来不会自动变成多写者。
2. 承诺边界：默认 single 的正确性不低于 LTS-2。`writers: 'multi'`、`SERIALIZABLE`、死锁错误码、savepoint 的文档语义在 `2.5.x` PATCH 中不缩小。PATCH 不加入复制或集群。与 LTS-2 并行维护；安全补丁两条线都要评估，README 告诉用户两条线的公告都要看。
3. 迁移 **2.2 → 2.5**：直接打开，或以文档中的 migrate 打开。逐步列出命令或 API。每一步之后默认写者模式仍是 single，需要 multi 必须显式打开，并链到 2.4 已冻结的锁协议说明（本版 README 保留足够上下文，使读者不必先读 2.4 计划）。
4. `getCompatibilityInfo()` 返回 `lts: true`，线名为 `2.5`。`version --json` 能区分 `ltsLine: '2.5'`。解释这些字段，避免和包版本字符串混成一个数。
5. CLI 面冻结，包含 `--writers`。列出本线读者会用的稳定入口，并写明 PATCH 不新增子命令。`doctor` 仍报告写者模式与锁持有者。
6. dist-tag：保留 `lts-2` 指向 2.2。`lts-3` 指向 2.5。团队确认主推荐仍是单写者时，`lts` **继续指向 2.2**。写明 `npm install` 不带 tag 时不会因为本版发布就改到 2.5。
7. 明确不在本版：新存储格式、复制、GraphQL、选主。需要多写者才升级；否则留在 LTS-2。
